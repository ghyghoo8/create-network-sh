本地资料已于 2026-10-29 脱敏，三个交付 ZIP 已删除。`your-github-login` 与 `mcp.example.com` 均为占位值，按上级 README 同步替换授权账号、网关域名、ngrok 入口、Host/Origin 及 OAuth App 配置。不要将占位模板覆盖到现有线上服务；本次没有执行下列部署步骤。

## 已运行网关的升级步骤

将展开目录中的 gateway_server.py、gitee_repository_tools.py、test_gateway_tools.py 和本指南放到 /opt/gitee-mcp-gateway/gateway。保留服务器现有 auth_policy.py、.env 和 migration_manifest.py；当前资料不再附带 ZIP。

在网关运行终端按 Ctrl+C，备份旧 gateway_server.py，然后覆盖代码。编辑现有 .env，将 GITEE_MODE 改为 WRITE；若截图对应新生成的 Gitee 令牌，也将 GITEE_ACCESS_TOKEN 更新为该新令牌。令牌只在服务器本机填写。

```bash
cd /opt/gitee-mcp-gateway/gateway
chmod 600 .env
/opt/gitee-mcp-gateway/.venv/bin/python test_gateway_tools.py
/opt/gitee-mcp-gateway/.venv/bin/python gateway_server.py
```

离线测试通过后启动。ngrok 固定入口不变。网关重启会丢失内存 OAuth 注册，需要在插件设置重新连接并刷新工具；如持续 invalid_client，移除并重新添加这个试验插件。先列工具并读取已有 README，随后执行你明确要求的写操作。下面的完整流程用于首次部署和项目文件迁移。

## 1 放置文件并停旧测试

首次部署时，从展开目录选取 auth_policy.py、.env.example、migration_manifest.py、gateway_server.py、gitee_repository_tools.py、test_gateway_tools.py、部署指南.md，完成占位配置后平铺放到服务器 /opt/gitee-mcp-gateway/gateway。不要把项目原 8 个文件放进此配置目录。保留之前 OAuth验证/本机验证资料。

在旧 smoke 或 oauth_server.py 运行终端 Ctrl+C，释放 8765；只停自己启动的测试进程。Hysteria、SSH、防火墙与其他服务均不用修改。

## 2 核对 GitHub OAuth App

若尚未创建，在 https://github.com/settings/developers → New OAuth App 填：
- 名称：G8 Gitee Gateway
- Homepage：https://mcp.example.com
- Callback：https://mcp.example.com/auth/callback

已有 App 的回调相同即可复用。用户自己取得 Client ID、Client Secret。服务只请求 read:user，不请求 repo 权限。此 App 用来验证谁能进入网关，Gitee PAT 则用来连接上游，两套身份不会相互替代。[官方 GitHubProvider](https://gofastmcp.com/integrations/github)

## 3 一次填写服务器配置

```bash
cd /opt/gitee-mcp-gateway/gateway
umask 077
if [ ! -e .env ]; then cp .env.example .env; fi
chmod 600 .env
nano .env
```

在本机编辑器填写 GITHUB_CLIENT_ID、GITHUB_CLIENT_SECRET、GITEE_ACCESS_TOKEN，保留 GITEE_MODE=READ。前两项来自 GitHub OAuth App，第三项来自你要用的个人 Gitee 账户。程序只读取 /opt/gitee-mcp-gateway/gateway/.env，不读取 Library 文件。不要把模板覆盖到已填写的 .env。

## 4 预检和启动网关

```bash
cd /opt/gitee-mcp-gateway/gateway
/opt/gitee-mcp-gateway/.venv/bin/python -m pip check
/opt/gitee-mcp-gateway/.venv/bin/python -c 'from importlib.metadata import version; print({n:version(n) for n in ["fastmcp","fastmcp-slim","mcp","python-dotenv","py-key-value-aio"]})'
/opt/gitee-mcp-gateway/.venv/bin/python test_gateway_tools.py
/opt/gitee-mcp-gateway/.venv/bin/python gateway_server.py
```

每条命令必须成功再运行下一条。现有完整 fastmcp 4.0.11 包应包含 server/client 依赖、python-dotenv、httpx2、py-key-value-aio memory extras；缺少模块就停止核对，不自动升级版本。程序检查准确版本，读取权限为 600 的普通 .env，监听 127.0.0.1:8765。

## 5 固定 ngrok 入口

如果已有同域名通道，先在它自己的终端 Ctrl+C 再启动，避免两个同域名实例：

```bash
ngrok http http://127.0.0.1:8765 --url=https://mcp.example.com --inspect=false
```

确认 Forwarding 域名完全一致。--inspect=false 关闭本机 HTTP inspection；另核 ngrok 控制台 Traffic Inspector 未启用采集。不添加 ngrok 自己的 OAuth 层，不改写路径，不开放 8765 公网端口。--inspect 是官方参数，如版本不接受先运行 ngrok http --help 核对。[官方 CLI](https://ngrok.com/docs/gateway/agent/cli)

## 6 检查本机及公网认证门

另开同服务器 SSH 终端：

```bash
curl --noproxy '*' --max-time 10 -s -o /dev/null -w '%{http_code}\n' -H 'Accept: application/json, text/event-stream' http://127.0.0.1:8765/mcp
curl --max-time 20 -s -o /dev/null -w '%{http_code}\n' -H 'Accept: application/json, text/event-stream' https://mcp.example.com/mcp
```

两者应为 401。若公网返回 ngrok 中间页、404、502或超时，先修通道，不进行 OAuth。若未认证即可获取受保护内容，停止网关。401 表示此检查正确地触发认证门，不是接入失败。

打开 https://chatgpt.com/plugins → 加号 → Add custom MCP server：

审阅后创建并安装插件，使用 your-github-login 完成 GitHub 登录授权。GitHub App Secret只填服务器 .env；不要猜填 ChatGPT 不明确的客户端字段。已有相同入口插件可先重新连接和刷新工具；网关重启后内存注册丢失，如持续 invalid_client，移除并重建本次试验插件。[ChatGPT 添加指南](https://developers.openai.com/api/docs/guides/custom-mcp-server)

在会话 @此插件，让它调用 whoami。真实返回必须为 status=ok、github_login=your-github-login。仅看到授权成功页面不算通过。错误 GitHub 账号不能调用工具，缺失 login 也拒绝。

## 8 验证 Gitee 后端

READ 模式仅注册读取入口；WRITE 模式增加写入入口。工具统一使用 gitee_ 前缀，whoami 与兼容的 create_private_project 保留原名。

| 权限 | 官方 MCP 工具（下表省略 gitee_ 前缀） |
| --- | --- |
| user_info | get_user_info、search_users、list_user_notifications |
| projects | list_user_repos、get_file_content、list_releases、search_open_source_repositories、search_files_by_content、compare_branches_tags；WRITE 增加 create_repo、fork_repository、create_release |
| pull_requests | list_repo_pulls、get_pull_detail、get_diff_files；WRITE 增加 create_pull、update_pull、merge_pull、manage_pull_review |
| issues / pull_requests 评论 | list_repo_issues、get_repo_issue_detail、list_comments；WRITE 增加 create_issue、update_issue、create_comment |

官方 MCP 的 25 个工具均按准确名称接入；READ 只启用其中 15 个读取工具。以下 19 个工具由 gitee_repository_tools.py 通过 Gitee REST API 补充：

| 能力 | 工具 | 模式 |
| --- | --- | --- |
| 仓库详情 | gitee_get_repository | READ / WRITE |
| 分支、提交、目录树、标签 | gitee_list_branches、gitee_list_commits、gitee_list_tree、gitee_list_tags | READ / WRITE |
| Webhook 列表与详情 | gitee_list_hooks、gitee_get_hook | READ / WRITE |
| 仓库设置与删除 | gitee_update_repository、gitee_delete_repository | WRITE |
| 创建分支、标签 | gitee_create_branch、gitee_create_tag | WRITE |
| 单文件增删改 | gitee_create_file、gitee_update_file、gitee_delete_file | WRITE |
| 批量文件提交 | gitee_commit_files | WRITE |
| Webhook 增删改与测试 | gitee_create_hook、gitee_update_hook、gitee_delete_hook、gitee_test_hook | WRITE |

因此完整清单应为 READ 23 个工具、WRITE 46 个工具，包含 whoami；WRITE 还包含兼容入口 create_private_project。权限勾选只决定令牌能调用哪些接口，不会让未实现的任意 Gitee API 自动变成工具。

单文件 content 的 encoding 默认为 utf8，程序转为接口要求的 Base64；二进制用 encoding=base64。更新和删除必须提供 gitee_get_file_content 返回的文件 Blob SHA，并指定相同分支，防止旧版本覆盖。gitee_commit_files 的 actions 支持 create/update/delete/move/chmod；action 内 encoding 使用 text 或 base64，修改现有文件时可提供 last_commit_id 进行版本检查。该字段是提交 SHA，与单文件 Blob SHA 不同。创建新分支需要已有 start_branch；空仓库首次批量提交行为尚未在线验证，原文件迁移可继续使用第 10–12 节 Git 路线。

Webhook 工具只调用 Gitee 的 Webhook 管理接口；测试工具会让 Gitee 向配置地址发送测试事件。响应中密码、签名密钥及 URL 查询参数会遮蔽。工具清单为读写操作设置对应 MCP annotations；更新、删除、合并及 Webhook 测试均标记其影响。

依次调用前两个，再列仓库，确认 Gitee 返回的账号就是预期 owner。GitHub 的 your-github-login 不一定等于 Gitee 用户名，不要混用。查找 a-share-investment-engine 是否已存在。官方实际工具名是 list_user_repos 和 create_repo，并非 list_user_repositories/create_repository。[Gitee 官方](https://github.com/oschina/mcp-gitee)

如果少了 Gitee 工具或失败，按故障节检查上游令牌/网络，不把仅 whoami 成功当后端成功。不要继续写操作。现有仓库必须先核实归属与内容，不能覆盖。

## 9 创建私有空仓库

两条路线任选其一，最终都在 Gitee 页面确认归属、private 和仓库 URL。

### 路线 A 受限 MCP 创建

先确认预期 Gitee 用户且同名仓库不存在。在服务器 .env 把 GITEE_MODE 改为 WRITE，停网关后重启。重新连接插件、刷新工具；可能需重新 OAuth。

可以调用通用 gitee_create_repo，明确指定 owner_type=user、private=true、name/path=a-share-investment-engine、auto_init=false。兼容入口 create_private_project 仍保留：以 confirm=true 调用时，它实时检查上游 schema，再固定提交相同的私有个人仓库参数。

创建前还会查询当前个人 Gitee ID；创建结果必须明确 private=true、固定路径且 owner.id 与该个人 ID 相同才返回 created_private。若错误、超时或“Creation not verified”，不要重试：先检查 Gitee 页面，可能仓库已创建。源码与远端 schema 可能变化；无法核实私有参数或结果就走路线 B，不回退公开创建。

后续需要维护仓库时可以继续保留 WRITE；只需要读取时改回 READ，重启并重新连接。工具操作范围仍由 Gitee 令牌与账户的实际仓库权限决定。

### 路线 B 用户网页手动建仓

登录你的个人 Gitee，创建名为 a-share-investment-engine 的仓库，明确选择私有，不选择组织，不初始化 README、许可证或 .gitignore。已有仓库则不重复创建，先核对内容。复制页面给出的 HTTPS 克隆地址，它应类似 https://gitee.com/你的Gitee用户名/a-share-investment-engine.git，不包含令牌。

官方 MCP 清单没有通用文件写入工具；本扩展版新增 gitee_create_file、gitee_update_file、gitee_delete_file 和 gitee_commit_files。单文件工具每次生成一个提交；gitee_commit_files 通过批量提交接口一次提交多个动作，DOCX 等二进制内容使用 Base64。它们不等同于本地 Git push。下面保留 Git 迁移路线，可从远端重新下载并逐文件核验原 8 个文件。

## 10 准备原 8 个文件和源清单

在你准备用来执行 Git 的机器上建立一个新的独立目录，放入原 8 个文件，保持目录层级和字节不变。本例使用 /opt/gitee-mcp-gateway/migration-src。这里不能放网关代码、.env、token、ZIP 或验收清单。用已交付备用包可恢复原件，但不把 ZIP 本身当项目文件上传。


## 11 标准 Git 提交与推送

只在新准备的独立 migration-src 操作；如果它已有 .git 或远端仓库不为空，停止本段并先核对，不能强制覆盖。

```bash
cd /opt/gitee-mcp-gateway/migration-src
git init -b main
git config core.autocrlf false
git config core.safecrlf true
git config credential.helper ''
git config user.name '填写你的提交显示名'
git config user.email '填写你选择的提交邮箱'
git add --all
git diff --cached --stat
git diff --cached --check
```

核对暂存恰好原 8 文件、无网关或凭据文件，姓名邮箱按你的真实选择填写，然后：

```bash
git commit -m 'Import initial project files'
git remote add origin https://gitee.com/你的Gitee用户名/a-share-investment-engine.git
git push -u origin main
git rev-parse HEAD
```

执行前将 remote 示例替换为步骤 9 页面返回的准确 HTTPS 地址。认证由用户在 Git 自身的交互提示中完成，按 Gitee 当时支持的方式输入，不把令牌写进 URL、命令参数或提交。上面的空 credential.helper 防止本仓库使用明文保存 helper；不自动配置 SSH 密钥。用户名邮箱是提交元数据，提交前自行确定。禁止 force push。

如果 push 报远端已有提交，停止并查看，不使用 --force 或自动合并来“修复”。

## 12 从远端重新下载并逐文件验收

另选一个尚不存在的目录 remote-verify；仍由用户在 Git 提示中认证：

```bash
git -c credential.helper= -c core.autocrlf=false clone --branch main --single-branch https://gitee.com/你的Gitee用户名/a-share-investment-engine.git /opt/gitee-mcp-gateway/remote-verify
git -C /opt/gitee-mcp-gateway/remote-verify rev-parse HEAD
/opt/gitee-mcp-gateway/.venv/bin/python /opt/gitee-mcp-gateway/gateway/migration_manifest.py verify /opt/gitee-mcp-gateway/remote-verify /opt/gitee-mcp-gateway/source-manifest.json
```

两个 commit SHA 必须相同，manifest verify 必须 PASS，Gitee 页面再次确认私有。只有三项一起通过才算 8 文件迁移完成。保留原件、备用 ZIP、源清单及 commit SHA，不在此流程清理来源。任何字节或文件数差异先查原因，不静默改编码或行尾。

## 13 关闭与后续运行

后台运行可使用本次 start.sh 与 stop.sh：放在 /opt/gitee-mcp-gateway/gateway，与网关代码同目录。首次切换时在原 gateway/ngrok 的前台终端分别按 Ctrl+C，再使用之前配置 ngrok 的同一账户执行：

```bash
cd /opt/gitee-mcp-gateway/gateway
chmod 755 start.sh stop.sh
./start.sh
```

启动成功后可关闭 SSH。停止用 ./stop.sh；重复启动会复用已核验的受控进程，重复停止也可正常执行。脚本用独立后台会话、进程身份校验与控制锁，只管理自己的运行记录；网关无认证 /mcp 返回 401 后启动 ngrok。ngrok 是否连接成功见其运行日志。

日志保存在同目录 logs：control.log 记录 UTC 启停时间、运行 ID、PID 和结果；gateway.latest.log 与 ngrok.latest.log 指向各自最近日志。每次启动生成独立日志，停止后保留历史。用 tail -F logs/gateway.latest.log 或 tail -F logs/ngrok.latest.log 查看输出，Ctrl+C 只结束查看。目录权限 700，日志/进程记录为 600；日志覆盖服务生命周期和进程输出。

实验版 OAuth 使用内存状态，每次进程只生成一次随机签名密钥，gateway 真正重启后需要重新连接授权。脚本不设置开机自启或自动重启；服务器重启后需手动 ./start.sh。长期自动运行需先设计加密持久化，再添加服务管理。

## 故障分支

- 本机端口拒绝/000：确认 gateway_server.py 仍在运行，旧测试是否占端口。只停止自己启动的旧实例。
- 公网 502/404：核 ngrok 域名、转发端口与完整 /mcp 路径；先使本机无认证返回401。
- 421/Origin 403：固定 ngrok 域名和代码一致；代码保留 Host/Origin 防护，不用 *、不禁用防护。
- OAuth 401/invalid_client：无认证测试的401正常；真实授权后仍401，核回调、GitHub账号及重启后旧注册。重新连接，必要时重建试验插件。
- Gitee 401：后端 PAT 缺失、过期或错误；用户在服务器编辑后重启。GitHub授权成功不会修复Gitee PAT。
- Gitee 403：核账号权限、仓库归属、作用域或服务策略，不直接勾选全部权限。
- Gitee工具缺失：检查是否同时上传 gitee_repository_tools.py，以及 .env 模式和上游网络。清单不完整时拒绝返回部分工具；服务器只记录静态清单中缺失的名称和数量，不打印令牌或响应正文。仅 whoami 不能证明上游连接。
- STARTUP FAILED：先跑版本/依赖检查，确认 .env 普通文件权限600、四个变量和端口；日志刻意不输出秘密或异常正文。
- 创建未核验：先网页查重及private，不重试、不自动删除。
- Git认证失败：只在官方Gitee账户设置核认证方式；不往URL塞凭据。

## 实现与验证范围

源码核对 FastMCP 4.0.11 wheel：GitHubProvider/load_access_token、create_proxy、mount、Visibility、StreamableHttpTransport。另核验 MCP2.3.0 的 streamable_http.py 会生成协议与 Session 请求头。专用 HTTP 工厂丢弃入站头，只用服务器 PAT 和对应模式的工具白名单。代理后端固定 mode=legacy，让 Gitee 按 2025-03-26 协议响应，避免现代前端导致 tools/list 缺失 cacheScope/resultType/ttlMs 的 ValidationError。前端可继续使用现代协议。

官方 MCP 初始地址固定为 https://api.gitee.com/mcp；MCP SDK 可按自己的限制处理同源且保留方法的 307/308，不接受跨源或降级跳转。补充 REST API 地址固定为 https://gitee.com/api/v5，不跟随重定向。两条线路均禁环境代理、不转发前端 OAuth 令牌、不自动重试写入。错误只暴露安全状态与类别，不暴露上游正文。

代理默认禁用全部组件，再按模式启用 15 或 25 个准确名称的工具，资源/模板/提示词不开放。REST 写工具在 READ 模式根本不注册。父网关 OAuth 校验所有 HTTP 请求，whoami、兼容建仓及每次 REST 调用另核身份。只读取服务器现有 .env，不从外部文件取得凭据。

离线测试使用固定版本框架和模拟 HTTP 上游，核验 READ/WRITE 工具清单、现代前端与旧协议后端、请求隔离、文件编码、版本参数、路径、错误和 Webhook 响应遮蔽。没有在线执行建仓、删除、文件写入、PR 合并或 Webhook 测试。官方远端工具与 API 会变化，部署后仍需重新发现工具并验证读取。
